# Halyk AI Challenge — проверка соблюдения кредитных ковенантов

Система читает «грязные» финансовые документы (200 PDF) и реестр транзакций за 2025 год и
определяет, соблюдены ли финансовые ковенанты по 12 корпоративным кредитам. Результат —
`submission.json`: **12 заёмщиков × 3 ковенанта = 36 ячеек**, в каждой `status`
(COMPLIANT/BREACH), `actual` (значение показателя) и `evidence_txn_id`.

**Ключевой принцип:** ИИ — это *инструмент чтения документов*, а не «чёрный ящик, который
выдаёт ответ». Всё, что влияет на цифру, считает детерминированный код по извлечённым фактам.
Результат работы LLM закэширован и закоммичен, поэтому **submission пересобирается одной
командой, без API-ключа и без интернета.**

## Быстрый старт

```bash
python -m src.build_submission     # собирает submission.json (детерминированно, оффлайн)
python score.py                    # официальная метрика против data/ground_truth.json
python validate.py                 # поячейная диагностика actual/status (для разработки)
```

Требуется только Python 3.9+ (стандартная библиотека) и симлинк `data → agentic-bank-public`
с датасетом организаторов. LLM-слой (`src/llm_extract.py`) запускается отдельно и опционально —
его выход уже лежит в `cache/enrichment/`.

## Архитектура: LLM читает, код считает

```
documents/*.pdf ─► [extract: LLM]  ─┐
  (состязательные   классификация    │  cache/enrichment/<sc>.json
   описания)        транзакций       ├─►  (категории, связанные стороны,   ─┐
                                     │     курсы EUR, реклассификации,      │
аудиторские PDF ─► [ручной разбор] ──┘     скаляры, начисления)             │
  (пороги, курсы,   пороги ковенантов                                      ├─► [engine] ─► submission.json
   реклассификации)  → specs/covenants.json ────────────────────────────── │   (детерминизм,
                                                                            │    воспроизводимо)
master_ledger_2025.csv ─► [ledger: фильтр сценария + обогащение] ───────────┘
                                                                    [score/validate] ─► сверка с ground_truth
```

Приоритет источников категории транзакции (в `ledger.py`): **аудиторская реклассификация >
категория из LLM-кэша > keyword-fallback**. Так задокументированные корректировки аудита
всегда перекрывают модель, а модель — эвристику. Ни один слой не «подглядывает» в ответы.

| Файл | Роль |
|---|---|
| `specs/covenants.json` | Пороги и математические определения всех 36 ковенантов из **действующих** договоров. Ядро логики. |
| `src/ledger.py` | Загрузка реестра, фильтр по сценарию, применение обогащения (FX, категории, связанные стороны, начисления). |
| `src/engine.py` | Детерминированный расчёт `status`/`actual`/`evidence` — диспетчер по 9 типам ковенантов. |
| `src/categorize.py` | Оффлайн keyword-категоризатор (fallback и базовая линия). |
| `src/llm_extract.py` | LLM-слой (Groq `llama-3.3-70b`): классифицирует каждую транзакцию, кэширует результат. |
| `src/build_submission.py` | Прогон 12 сценариев → `submission.json`. |
| `cache/enrichment/<sc>.json` | Закэшированный выход слоя чтения (категории, связанные стороны, реклассификации, курсы, скаляры). Коммитится → воспроизводимость. |
| `score.py`, `validate.py`, `debug_cats.py` | Официальная метрика, поячейная диагностика, разбор категорий. |

## Как считаются ковенанты (движок)

Реализованы все типы из договоров:

- `ratio` / `related_party_ratio` — коэффициент (числитель/знаменатель по категориям).
- `aggregate_min` / `aggregate_max` — сумма по категории (с фильтром периода, напр. Q4).
- `max_single_line` — наибольшая из статей по отдельности.
- `min_less_largest` — база минус наибольшая из перечисленных статей.
- `related_party_abs` — платежи связанным сторонам (**только оттоки**).
- `springing_ratio` — тест применяется только при срабатывании триггера.
- `point_in_time_liability` — сумма расходов периода + обязательство на дату.

Правила кейса, зашитые в движок: `actual` всегда положителен (2 знака); `status` считается по
**неокруглённому** значению; `min` → BREACH при `actual < threshold`, `max` → при `>`.

## Разобранные ловушки (именно они отличают решение)

Датасет намеренно состязательный. Что распознаётся и как:

| Ловушка | Обработка |
|---|---|
| **Устаревшие редакции договоров** (2024 г.) | Отсев по маркеру «НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ»; берём только действующий договор. |
| **Черновики аудита** («ПРОМЕЖУТОЧНАЯ ВЕДОМОСТЬ», проект) | Игнорируются. Применяются только **финальные** «Примечания к финансовой отчётности» и «отчёты о выполнении согласованных процедур». |
| **Отклонённые реклассификации** («рассмотрена и отклонена») | Не применяются — первоначальная классификация сохраняется. |
| **Порог связанной стороны свой у каждого заёмщика** (20/25/30/32/34/35/36/38%) | Берётся из текущего KYC-досье конкретного заёмщика, а не константа. |
| **Имена в кавычках** в таблице долей (`"Turan Capital" LLP`) | Парсер их не теряет. |
| **Контрагенты — шум** | Категория читается из *описания операции*, а не из имени контрагента. |
| **Маркетинг раздувает EBITDA** (мега-траты 9–12M при выручке 9M) | Маркетинг — отдельная категория, не входит в операционные расходы. |
| **Возвраты/ребейты/сторно** | Категория — по природе операции; «платежи» = только оттоки. |
| **Валюта EUR** | Пересчёт по курсу фактического расчёта из аудиторского примечания. |
| **Начисления с пустой суммой** (`TXN-P7-0033`, `TXN-P8-0031`) | Сумма берётся из аудита (`amount_overrides`). |
| **Скрытые обязательства** (программа выходных пособий) | Добавляются как скаляр из примечаний аудита. |

## Результаты и валидация

Прогон против `ground_truth` (используется **только для отладки логики**, не для подгонки —
цифры не хардкодятся, правила обобщаемы):

| Группа ковенантов | Верных ячеек |
|---|---|
| 6.2 (агрегатные суммы, наибольшая статья) | **12 / 12** |
| 6.3 (платежи связанным сторонам) | **10 / 12** |
| 6.1 (коэффициенты, EBITDA, скаляры) | **7 / 12** |
| **Итого статус** | **29 / 36** |

Каждая закрытая ячейка обоснована конкретным документом (номер KYC-досье / аудиторского
примечания указан в `cache/enrichment/<sc>.json`).

## Честные ограничения

7 ячеек не решены **не из-за категоризации, а из-за отсутствия данных в выданных документах** —
это подтверждено и keyword-, и LLM-разбором (оба упираются в одни и те же ячейки):

- **P5 6.1, P9 6.1** — требуются капзатраты **Группы** и статус «Неограниченной дочки»: данные
  уровня консолидации, не раскрыты ни в одном PDF и не выводятся из реестра.
- **P2 6.3, P6 6.1** — у этих заёмщиков KYC без таблицы долей, связанная сторона нигде не названа.
- **P1 6.1, P4 6.1** — нераскрытые реклассификация в капитал и полный перечень разовых статей.

Довести их можно было бы только скопировав ответы из `ground_truth` — что нарушает правила и
провалится на скрытом наборе. Решение сознательно этого не делает.

## Принципы, заложенные в решение

1. **Воспроизводимость важнее «магии»** — оффлайн-сборка одной командой, без докера и серверов.
2. **ИИ как компонент, а не как ответ** — LLM только классифицирует; вердикт выносит проверяемый код.
3. **Приоритет доказательства** — каждая корректировка привязана к конкретному документу.
4. **Никакой подгонки под ground_truth** — правила общие, метрика лишь измеряет их качество.
