# Halyk AI Challenge — проверка соблюдения кредитных ковенантов

Решение читает «грязные» финансовые документы и реестр транзакций и по каждому ковенанту
каждого заёмщика выносит вердикт **COMPLIANT / BREACH**, обосновывающее **число** и
**транзакцию-улику**. Формат вывода — один `submission.json` по шаблону организаторов.

Пайплайн переключается между наборами данных переменными окружения:
- **приватный (боевой)** набор `agentic-bank-hidden` — 27 заёмщиков, 81 ячейка → **это и есть сдаваемое решение** (`submission_hidden.json`);
- **открытый** набор `agentic-bank-public` — 12 заёмщиков, использовался для отладки и валидации метрикой (в нём был `ground_truth.json`).

**Главный принцип:** ИИ — инструмент *чтения* документов, а не «чёрный ящик, выдающий ответ».
Всё, что влияет на цифру, считает детерминированный код. Выход LLM закэширован и закоммичен,
поэтому **submission пересобирается одной командой, без API-ключа и без интернета.**

## Быстрый старт

Сборка боевого решения из закэшированных данных (ключ и сеть НЕ нужны):

```bash
HALYK_DATA=agentic-bank-hidden \
HALYK_SPECS=specs/covenants_hidden.json \
HALYK_ENRICH=cache/enrichment_hidden \
HALYK_OUT=submission_hidden.json \
python3 -m src.build_submission
```

Проверка на открытом наборе против `ground_truth` (метрика по официальной формуле):

```bash
python3 -m src.build_submission && python3 score.py     # публичный набор
```

Требуется только Python 3.9+ (стандартная библиотека). Слои LLM (ниже) уже отработаны, их
результат лежит в `cache/`.

## Архитектура: LLM читает, код считает

```
agreements.pdf ─► [llm_specs]   ─► specs/covenants_hidden.json  (виды/пороги/метрики)   ┐
KYC.pdf        ─► [kyc_related] ─► cache/enrichment/*.json       (связанные стороны)     │
ledger.csv     ─► [llm_extract] ─► cache/enrichment/*.json       (категория операции)    ├─► [engine] ─► submission.json
audit.pdf      ─► [ручной/LLM]  ─► cache/enrichment/*.json       (реклассы, начисления,  │   (детерминизм)
                                                                  курсы, скаляры)         ┘
```

Приоритет источника категории транзакции (в `ledger.py`): **аудиторская реклассификация >
категория из LLM-кэша > keyword-fallback**. Задокументированные корректировки всегда
перекрывают модель, модель — эвристику. Ни один слой не «подглядывает» в ответы.

| Файл | Роль |
|---|---|
| `src/llm_specs.py` | LLM извлекает определения ковенантов из договоров в схему движка (виды, пороги, метрики). |
| `src/llm_extract.py` | LLM (Groq `llama-3.3-70b`) классифицирует каждую транзакцию в закрытую таксономию категорий. |
| `src/kyc_related.py` | Детерминированный разбор KYC-досье: связанные стороны по порогу голосующих прав данного заёмщика. |
| `src/categorize.py` | Оффлайн keyword-категоризатор (fallback без сети). |
| `src/ledger.py` | Загрузка реестра, фильтр по сценарию, применение обогащения (категории, FX, связанные стороны, начисления). |
| `src/engine.py` | Детерминированный расчёт `status`/`actual`/`evidence` — диспетчер по 11 типам ковенантов. |
| `src/build_submission.py` | Прогон всех сценариев → `submission.json` (набор данных выбирается окружением). |
| `specs/covenants_hidden.json`, `cache/enrichment_hidden/` | Закэшированный вход боевого набора (коммитится → воспроизводимость). |
| `score.py`, `validate.py`, `debug_cats.py` | Метрика, поячейная диагностика, разбор категорий. |

## Типы ковенантов (движок)

`ratio` · `related_party_ratio` · `springing_ratio` · `aggregate_min` · `aggregate_max` ·
`max_single_line` · `min_less_largest` · `related_party_abs` · `point_in_time_liability` ·
`quarterly_min` · `quarterly_max` (показатель считается отдельно за каждый квартал, берётся
худший).

Правила: `actual` всегда положителен (2 знака); `status` — по НЕокруглённому значению;
`min` → BREACH при `actual < threshold`, `max` → при `>`; платежи связанным сторонам считают
только оттоки.

## Разобранные ловушки (то, что отличает решение)

| Ловушка | Обработка |
|---|---|
| Устаревшие редакции договоров/досье | Отсев по маркерам «НЕДЕЙСТВУЮЩАЯ РЕДАКЦИЯ» / «SUPERSEDED». |
| **Черновики аудита** («ПРОМЕЖУТОЧНАЯ ВЕДОМОСТЬ», DRAFT) | Игнорируются: применяются только финальные примечания и отчёты о согласованных процедурах. |
| **Отклонённые реклассификации** | Не применяются (обе реклассификации начислений в боевом наборе оказались отклонёнными черновиками). |
| Порог связанной стороны свой у каждого заёмщика | Берётся из его KYC-досье (20–38%), а не константа; имена в кавычках парсер не теряет. |
| Контрагенты — шум | Категория читается из описания операции, а не из имени контрагента. |
| Возвраты/ребейты/сторно как «выручка» | Классифицируются по природе операции; крупные reversal-притоки не засчитываются выручкой. |
| Начисления с пустой суммой в реестре | Значение берётся из аудита (`amount_overrides`), категория — из финального документа. |
| Валюта EUR | Пересчёт по курсу из аудита. |
| Иностранный заёмщик с англоязычными документами | LLM-слой многоязычен; спек извлекается из английского договора. |
| Квартальные ковенанты (мин. EBITDA/выручка за квартал) | Отдельный расчёт по кварталам, берётся худший. |

## Оценка и ограничения

На открытом наборе (где был `ground_truth`) детерминированное ядро проверено метрикой по
официальной формуле. Для боевого набора эталона нет, поэтому корректность обеспечивается
методологией: каждая закрытая ячейка обоснована конкретным документом, а спеки сверены с
текстом договоров.

Несколько ячеек боевого набора заполнены **оценочно (best-effort)** — там требуются данные
уровня Группы/консолидации или статус «Неограниченной дочки», которых нет в выданных
документах (их точное значение можно было бы получить только подглядев в ответы, чего решение
принципиально не делает). Такие ячейки заполнены разумными значениями, а не `null`.

## Принципы

1. **Воспроизводимость важнее «магии»** — оффлайн-сборка одной командой, без докера и серверов.
2. **ИИ как компонент, а не как ответ** — LLM читает документы; вердикт выносит проверяемый код.
3. **Приоритет доказательства** — каждая корректировка привязана к документу.
4. **Никакой подгонки под ground_truth** — правила общие, метрика лишь измеряет их качество.
